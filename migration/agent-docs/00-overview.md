# Migration overview: Sphinx/nbsphinx to MyST (Jupyter Book 2 engine)

Started: 2026-09-11. Branch: `feat/migrate-to-jupyterbook`.

This folder is the complete, running record of the migration of `docs.maap-project.org`
from Sphinx + nbsphinx + sphinx_rtd_theme to MyST (`mystmd`, the engine behind
Jupyter Book 2). It is written as work happens: plans, decisions, spike results,
issues found and, most importantly, every compromise in fidelity.

Files:

| File | Purpose |
|---|---|
| `00-overview.md` | Goal, scope, phasing, how to re-run the migration (this file) |
| `01-inventory.md` | What the Sphinx site contains and every quirk that matters |
| `02-decisions.md` | Dated decision log, with the reasoning |
| `03-spike-results.md` | What real builds showed for each open question, with evidence |
| `04-compromises.md` | LOUD list of everything that is not a faithful reproduction |
| `05-verification.md` | What was checked, how, and the per-page results |

## Goal

Phase 1 is a faithful, like-for-like migration: same pages, same navigation, same
content, same stored notebook outputs, no build-time execution. The audience is
science users who care about details; nothing is dropped or reworked to suit a
technical choice without a real-build test first, and every compromise is recorded
in `04-compromises.md`.

Later phases (not in scope here): anywidget static-export plugin, theme polish,
rewriting absolute `docs.maap-project.org` links, PDF export, a convenient
"execute on the MAAP hub and commit" workflow for end users, possibly moving the
static build to S3.

## Scope of phase 1

- Convert the 20 `.rst` files to MyST Markdown.
- Reproduce the full toctree hierarchy as `project.toc` in `docs/source/myst.yml`.
- Rewrite relative cross-links inside notebook markdown cells so they resolve under
  MyST (anchor slugs change). Absolute URLs are left alone.
- Keep every old URL working via generated redirect stubs (MyST changes
  `foo_bar.html` to `/foo-bar/`).
- Keep hosting on ReadTheDocs using `build.commands`.
- Replace Sphinx config and tooling (`conf.py`, `docs/Makefile`, `requirements.txt`)
  with `myst.yml`, `pyproject.toml` + `uv.lock`, and a top-level `Makefile`.

## How the migration is produced

Everything is generated by deterministic scripts in `migration/` so the conversion
can be re-run from the pristine Sphinx tree (for example after other PRs merge):

```
make migrate      # = git checkout develop -- docs/source && git clean -fd docs/source
                  #   && uv run python migration/migrate.py --strict
make build        # myst build --html + redirect stubs
make verify       # structural checks + notebook output audit against the build log
```

Post-build steps (`gen_redirects.py`, `verify.py`) run against `_build/html`.
Re-running `make migrate` on an unchanged `develop` reproduces a byte-identical
`docs/source` (verified 2026-09-11, tree hash `ad31ad302763a1a9` before and after).
See `02-decisions.md` for the script design and `05-verification.md` for results.

## Notebook execution policy

Notebooks are executed by hand on the hosted MAAP JupyterHub and the executed
`.ipynb` files are committed. Nothing executes notebooks in CI, at build time, or
locally. The site renders whatever outputs are stored in the repo, exactly as the
Sphinx site did (`nbsphinx_execute = 'never'`).
